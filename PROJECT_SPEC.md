# Traffic Sign Recognizer — Complete Project Specification

> A language-agnostic, implementation-focused specification of the whole project.
> It is meant to be comprehensive enough to **rebuild the project in another
> programming language**. Source code is described conceptually; no raw source
> is reproduced here. Where a decision matters for a faithful rebuild it is noted.

---

## 1. High-Level Overview

The **Traffic Sign Recognizer (TSR)** is a command-line program, written in Go,
that:

1. **Extracts** hand-crafted numerical features from images of German traffic
   signs.
2. Stores every feature set as one row in a CSV file (the *feature-vector*).
3. **Classifies** unlabelled/known feature sets into one of six known
   traffic-sign categories using two interchangeable algorithms:
   - **K-Nearest-Neighbors (KNN)** over z-score-standardized Euclidean distance.
   - A **decision tree** trained with batch CART / Gini impurity.

The whole pipeline is built on the **Go standard library only**, plus one
third-party dependency, `golang.org/x/image/bmp`, which supplies a BMP codec
(the Go standard library ships no BMP decoder). No external ML/DL libraries are
used — everything (color classification, geometry features, distance math,
tree learning) is implemented by hand.

The target domain is **six** German traffic signs:

| Class label | Meaning |
|---|---|
| `Stop` | Stop |
| `Vorfahrt gewähren` | Give way / yield |
| `Vorfahrtsstraße` | Priority road |
| `Vorfahrt von rechts` | Yield to the right |
| `Fahrtrichtung links` | Turn left |
| `Fahrtrichtung rechts` | Turn right |

### Design goals of the architecture

- A single, fixed **feature vector** type is produced by extraction and consumed
  by both classifiers.
- Classification reads from CSV (no direct image re-reading), so extraction,
  classification, and later tools (e.g. the visualizer) all share one schema.
- Training and application are **decoupled**: a trained model is serialized to
  disk and reloaded later. This makes training a one-time, offline step.

## 5. Data Extraction (`src/data_extraction`)

Two files:

- `colors.go` — color classification logic (HSV + hard thresholds).
- `api.go` — directory walking, parallel extraction, CSV writing.

### 5.1 Input layout for extraction

The extractor is given **one directory** that contains a set of subfolders. Each
subfolder's **name is a class label** (e.g. `Stop`). Within each subfolder are
image files at arbitrary depth (there are nested folders such as
`<class>/0/80x60+1/`, etc.). All images share:

- A **pure white background**.
- A single centered traffic sign.
- Up to five distinct colors per sign (red/blue/yellow/black + the white frame).
- Extensions among `.bmp .png .jpg .jpeg .gif .tif .tiff`.

### 5.2 Supported image formats

PNG, JPEG/JPG, GIF, TIFF/TIF, and **BMP** (via `golang.org/x/image/bmp`). The Go
standard library's own decoders cover all of these except BMP; hence the blank
import `_ "golang.org/x/image/bmp"`.

### 5.3 Worker pool for parallel extraction

- `workerCount()` returns `runtime.NumCPU()`, floored to at least `1` — so the
  number of worker goroutines equals the machine's CPU threads.
- A channel `jobsCh` distributes per-image job **indices** across workers.
- Each job computes one vector; results are written back into a preallocated
  slice by index (not append) so ordering matches the original job order after
  all workers finish (`sync.WaitGroup`).
- Extraction failures (unreadable image / decode error) print a warning to
  **stderr** and the affected row is simply skipped.

### 5.4 Feature vector (`DataVectorV1`) — computed per image

For every image the following pipeline runs (see `data_model` for storage):

1. **Color analysis (full image).**
   - Each pixel is classified into one of {red, yellow, blue, white, black} or
     `unknown`.
   - Records whether each primary color category (red/blue/yellow/black) is
     present anywhere in the image.
   - Counts the number of *distinct* categories among those five present.
   - `unknown` pixels are ignored (no flag, no count).

2. **White-frame removal.**
   - Scans all four edges inward to find the bounding box of non-white pixels.
   - A pixel counts as white if its minimum RGB channel value is `> 180` (this
     matches pure white and near-white backgrounds such as `(197,197,195)`).
   - Strips the surrounding frame; returns an inner rectangle of strictly
     non-white content. If no non-white pixel exists, it falls back to the full
     image bounds so subsequent detectors return deterministic zeros.

3. **Vertical color-change detection.**
   - Places **10 vertical lines** evenly across the cropped width (at 1/11, 2/11,
     … 10/11 of the width) and scans each top-to-bottom, counting category
       transitions between adjacent segments.

4. **Horizontal color-change detection.**
   - Places **10 horizontal lines** evenly across the cropped height (at
     1/11…10/11 of the height) and scans each left-to-right the same way.

5. **White fractions (3×3 grid).** Nine grid squares; for each, the fraction of
   white pixels (value in `[0, 1]`).

6. **Left–right asymmetry (3×3 grid).** For each of nine cells: left-half white
   fraction minus right-half white fraction (values in `[-1, 1]`). Positive means
   white mass is biased to the right (e.g. a left-pointing arrow), negative means
   biased left.

**Detail — line scanning (`countLineChanges`):** each line is sampled in
segments; for each segment it computes the **average RGB** over all pixels in
that segment, then classifies that average color into a single category. It then
counts how many times consecutive segments differ in category. A small
`seg = lineLen/100` (floored to `1`) averaging is used for noise tolerance.
White-to-white transitions **do not** count as changes because the category stays
the same.

### 5.5 Color classification (`colors.go`) — full detail

Conversion:

- `toHSV(c color.RGBA)` returns `(h, s, v)` where hue `H ∈ [0,360)`, and S, V are
  in `0..255` scale (V = max channel; S = 255·(max−min)/max when max>0 else 0).

Classification (`isColor`) applies an **achromatic-first then hue** strategy:

| Category | Condition | Notes |
|---|---|---|
| Black | `V < 45` (any H, any S) | dark / achromatic |
| White | `S < 45 && V > 150` | bright achromatic |
| Red | `H ∈ [340,360] ∪ [0,20] && S > 50 && V > 50` | wraps around 0°, red→orange |
| Yellow | `H ∈ [28,60] && S > 25 && V > 55` | warm sign-yellow tolerated |
| Blue | `H ∈ [190,250] && S > 45 && V > 45` | deep to light blue |
| Unknown | none of the above | ignored |

Note the order: black/white are resolved first; then red (hue near 0/360),
yellow, and blue in that sequence. The switch short-circuits on the first match,
so a pixel satisfying multiple bands takes the first listed one. There are two
helper booleans (`isRed`, `isWhite`, `isBlue`, `isYellow`, `isBlack`) for
compatibility/testing but the core classifier is `isColor`.

### 5.6 The `imageToRGBA` normalization step

All inputs are decoded to an arbitrary `image.Image`, then copied into a tightly
-packed `*image.RGBA` covering the image bounds via `draw.Draw`. This unifies
pixel access to `RGBAAt(...)` across all formats.

## 6. Data Model (`src/data_model`)

Two files:

- `data_vector_v1.go` — the `DataVectorV1` struct and its CSV row encoder.
- `api.go` — a minimal `DataVectorApi` interface requiring `WriteRow(*csv.Writer)`.

### 6.1 Fields

`DataVectorV1` holds (all unexported, single constructor `NewDataVector`):

| Field | Type | Meaning |
|---|---|---|
| `picturePath` | string | relative path of the image |
| `trafficSign` | string | class label (subfolder name) |
| `numberOfDifferentColors` | int | count of distinct color categories |
| `containsRed` / `containsBlue` / `containsYellow` / `containsBlack` | bool | presence flags |
| `numberOfColorChangesVertically` | []int (len 10) | vertical line-change counts |
| `numberOfColorChangesHorizontally` | []int (len 10) | horizontal line-change counts |
| `whiteFractions` | []float64 (len 9) | white fraction per 3×3 cell |
| `leftRightAsymmetry` | []float64 (len 9) | left–right asymmetry per cell |

### 6.2 CSV encoding (`WriteRow`) — field order & formatting

The record is a slice of strings in this exact order:

1. `Traffic_Sign` — raw class label.
2. `Path` — image path.
3. `Number_of_different_colors` — integer as decimal string.
4. Four flags (`red`, `blue`, `yellow`, `black`) encoded as `"1"`/`"0"`.
5. Ten vertical counts, each formatted as `value/10` with **one** decimal place
   (`strconv.FormatFloat(x, 'f', 1, …)`). *(Note: the underlying int is divided
   by 10 — i.e. a scaling applied during write; preserve it for faithful rebuilds.)*
6. Ten horizontal counts — same `/10`, one-decimal formatting.
7. Nine white fractions — formatted to **two** decimals (`'f', 2`).
8. Nine left–right asymmetry values — formatted to **two** decimals.

The total field count per row is **45**: two string fields (`Traffic_Sign`,
`Path`) plus `1 + 4 + 10 + 10 + 9 + 9 = 43` numeric features.

### 6.3 CSV header (`writeCsv`)

`writeCsv` emits a header row with exactly these names (then one row per
successfully extracted vector; skipped/failed rows are silently omitted):

```
Traffic_Sign,Path,Number_of_different_colors,Contains_red,Contains_blue,Contains_yellow,Contains_black,
Number_of_color_changes_vertically_0..9,
Number_of_color_changes_horizontally_0..9,
White_fraction_0..8,
Left_right_asymmetry_0..8
```

### 6.4 Blank assignment

`var _ DataVectorApi = DataVectorV1{}` asserts the type satisfies the interface;
it is a lightweight compile-time contract.

## 7. KNN Classification (`src/data_classification`)

Three files:

- `api.go` — `DataClassifierApi` and `ClassificationResultApi` interfaces.
- `classification.go` — KNN algorithm + standardization.
- `classification_result.go` — result type + formatting.

### 7.1 Interfaces

- `ClassifyCsvWithKnn(k int, svToBeClassify, csvAlreadyClassified string) (float32, []ClassificationResultApi, error)`
  - returns: accuracy `float32` (percent), results slice, and an error.
- `ClassifyWithDecisionTree(k int, svToBeClassify, decisionTree any) (float32, []ClassificationResultApi, error)` — declared for symmetry with the dtree pipeline but not part of the main CLI flow.

### 7.2 Algorithm (`classifyCsvWithKnn`)

1. **Default k** = `5` if `k <= 0`.
2. **Parse features**: reads both CSVs via `readFeatures`. The first column is the
   label, second is the path, columns `2..` (index 2 onward) are numeric
   features. Rows with fewer than 3 fields are skipped; the header row is skipped.
3. **Z-score standardization** — computed from the **training** set only:
   - `mean[j] = average` of feature column j.
   - `stddev[j] = population std` (`sqrt(sum((x-mean)^2) / n)`), i.e. divided by `n`, not `n-1`.
   - Transformed test vectors use the **same** training statistics (fit-on-train).
   - Columns with zero variance → mapped to `0` (avoid divide-by-zero; they then
     contribute nothing).
4. **Per test row**: `classifyOne(query, train, k)`.
5. **Accuracy** = `correct / total * 100`, stored as `float32`. Empty test set → `0`.

### 7.3 `classifyOne` (KNN + majority vote)

- Computes **Euclidean distance** between the query and every training vector:
  `sqrt(sum((a_i − b_i)^2))`.
- Sorts all distances ascending (`sort.Slice`).
- The first `k` entries (by sorted order, breaking ties by closest distance) are
  collected; votes tallied per class label.
- Majority class wins; ties broken by **alphabetical** key order (via
  `sortedKeys`) so output is deterministic — the most-voted highest-tie label is
  the lexicographically smallest.

The result records per test image: file path, whether correctly classified, the
true label (`ShouldBe`), and predicted label (`Is`).

### 7.4 Result formatting

- `Stringify()` → `"Image <path> | Should be <label> | Classified as <label>"`.
- `StringifyIfFaulty()` → same string only when misclassified, else empty (used by
  the `-printfaulty` log feature).
- Blank assignment: `var _ ClassificationResultApi = ...`.

## 8. Decision Tree Classification (`src/data_classification_dtree`)

Four files:

- `api.go` — `DecisionTreeApi` + result interface.
- `decision_tree.go` — batch CART training, serialization, CSV I/O, classification.
- `classification_result.go` — shared result type (mirrors KNN package).
- `decision_tree_test.go` — unit test.

### 8.1 Interfaces

- `TrainCsv(pathToTrain, treeFile string) error` — builds the tree and writes it to `treeFile`.
- `ClassifyCsv(treeFile, pathToClassify, pathToOutput string) (float32, []ClassificationResultApi, error)` — loads tree, predicts, writes every prediction one-per-line to `pathToOutput`, returns accuracy.

### 8.2 Model (`treeNode` & `Tree`)

JSON-serialized structure:

| Field | JSON key | Meaning |
|---|---|---|
| `Feature int` | `"feature"` | node index; `<0` means leaf |
| `Thresh float64` | `"thresh,omitempty"` | split threshold (`omitempty` so leaves omit it) |
| `Left *treeNode` | `"left,omitempty"` | left child |
| `Right *treeNode` | `"right,omitempty"` | right child |
| `Counts map[string]int` | `"counts,omitempty"` | class histogram at a leaf |

- **Internal node:** `Feature >= 0`; route left if feature value `<= thresh`, else right.
- **Leaf node:** `Feature == -1`; holds class counts; `majority()` returns the
  most frequent label, ties broken alphabetically (`sortedKeys`).

### 8.3 Training parameters

- `minSamplesToSplit = 30` — a node needs at least this many samples before it may split.
- `maxDepth = 12` — bounds tree depth to limit overfitting.

### 8.4 Batch CART algorithm (`build` + `bestSplit`)

**`build(samples, depth)`**:
1. Tally class counts (leaf default).
2. Stop if `depth >= maxDepth`, or `len(samples) < minSamplesToSplit`, or only one
   distinct class remains — return the leaf.
3. Otherwise call `bestSplit`. If it returns a negative feature index or non-positive
   gain, return the unsplit leaf.
4. Partition samples into left (`feature <= thresh`) and right (else).
5. Recurse on both children with `depth + 1`.

**`bestSplit(samples, counts)`**:
- Base Gini = `gini(counts, len(samples))`.
- For each feature: sort the sample indices by that feature; sweep candidate split
  points between consecutive distinct values; maintain running left/right counts.
- At every jump in feature value evaluate the **weighted Gini** of the two resulting
  partitions. Track the minimum weighted Gini and record the best `(feature, thresh)`
  (threshold = midpoint between the two adjacent sorted values).
- Returns `(feature, thresh, gain = base − bestWeighted)`.

**`gini(counts, total)`**: `1 − Σ (count/total)^2`; returns `0` if `total == 0`.

The **batch** property: each split is evaluated over *all* samples currently at the
node (computed once), not incrementally as samples arrive — so the tree is
**independent of input row order**.

### 8.5 Prediction (`predict`)

Walk from the root; at each internal node route left/right on `feature <= thresh`;
stop at a leaf and return its `majority()` class.

### 8.6 Serialization

- `Save(path)`: `json.MarshalIndent(root, "", "  ")` → written with mode `0o644`.
- `LoadTree(path)`: reads the file then `json.Unmarshal` into `*treeNode`.

The on-disk format is a pretty-printed JSON tree (see the existing
`output/tree.json`).

### 8.7 CSV I/O (`readSamples`)

Identical parsing to KNN: header skipped, first column = label, second = path,
columns `[2:]` parsed as float64 features; rows with `<3` fields skipped.

### 8.8 `ClassifyCsv` (application)

1. `LoadTree(treeFile)`, `readSamples(pathToClassify)`.
2. Predict each sample. Mark correct if prediction == label.
3. Write **every** prediction (`Stringify()`, one per line) to `pathToOutput`.
4. Return accuracy as percent (float32), results, error.

### 8.9 Result formatting & test

`ClassificationResult` is identical to the KNN package's (same fields, same
`Stringify`/`StringifyIfFaulty`). The unit test (`TestTreeTrainRecover`) builds a
random synthetic labelled dataset of **5000** samples with 4 features and asserts
that training does not panic/crash — a smoke test for the CART routine.

## 9. Entry Point & CLI Parsing (`src/cmd/main`)

File: `traffic_sign_recognizer.go`. Package `main`. Two functions: `main` and
`run(args)`, with two logging helpers.

### 9.1 Flow

- `main()` calls `run(os.Args[1:])`; on error prints `error: <msg>` to stderr and
  exits with status `1`. On success it returns `0`.

### 9.2 Argument parsing (two-pass, manual — no flag package)

**First pass** extracts the standalone boolean flag `-printfaulty` from the raw args;
everything else is collected into `filtered`, preserving order.

**Second pass** walks `filtered` and dispatches on known mode flags:

| Flag | Consumes | Variables set |
|---|---|---|
| `-e <path> <csv>` (2) | extract → writes CSV | `extractDir`, `extractCsv` |
| `-knn <in> <out>` (2) | KNN classify | `classifyIn`, `classifyOut` |
| `-dtree-train <train> <treeFile>` (2) | train tree | `dtTrain`, `dtTreeFile` |
| `-dtree-classify <tree> <test> <out>` (3) | classify w/ tree | `dtTreeFile2`, `dtTest`, `dtOut` |
| trailing integer | treated as the KNN **k** value | `k` |

- An unknown string triggers `fmt.Errorf("unknown argument %q", ...)` → returns error.
- The integer parser trims whitespace and uses `strconv.Atoi`; failure → error.

**Dispatch** — matches the first non-empty mode; if none matched, it errors with
`"nothing to do: use -e, -knn, -dtree-train or -dtree-classify"`.

### 9.3 Mode implementations

- **Extraction:** `dataextraction.New().ExtractToCsv(extractDir, extractCsv)`.
- **KNN:** `dataclassification.New().ClassifyCsvWithKnn(k, classifyIn, classifyOut)`,
  then optional `-printfaulty` logging, then prints `"Correctly classified: N%"`
  (rounded `int(accuracy + 0.5)`).
- **DT train:** `datatree.NewDT().TrainCsv(dtTrain, dtTreeFile)`; prints success path.
- **DT classify:** `datatree.NewDT().ClassifyCsv(...)`; optional logging; prints %.

### 9.4 Logging helpers

- `logFaulty(results []dataclassification.ClassificationResultApi, path)` — opens/writes
  each result's `StringifyIfFaulty()` line-by-line to `path`.
- `logFaultyTree(results []datatree.ClassificationResultApi, path)` — same for the tree API.
- Both create the file fresh, defer-close it, and skip empty lines.

## 11. Data Assets & Augmentation Scheme

### 11.1 Directory contents

- `assets/training_data/` — labelled training images, one subfolder per class (6 folders).
- `assets/to_be_classified_data/` — test images, same 6-class folder structure.
- `assets/all_signs_png/` — six reference PNGs (one per sign) for manual/diagnostic use.

### 11.2 Augmentation naming

Training & test images are organized in a nested augmentation scheme:

```
assets/training_data/<class>/<mode>/<size-or-scale>/<image>.<ext>
```

- `mode` ∈ `{0, +1, -1, +2, -2, 3500}` (rotation/transform variants).
- size/scale folder names look like `80x60`, `80x60+1`, `80x60+2`, `80x60+3` — the
  `<W>x<H>` base plus a small offset variant.

Image files follow the convention `X<n>Y<m>.bmp` where `n`/`m` are integer offsets,
e.g. `X-10Y-10.bmp`, `X40Y-30.bmp`. Extraction walks these recursively and includes
every supported image regardless of folder name.

### 11.3 Dataset splitter (`mix_datasets.py`)

A pure-Python (stdlib: `os`, `random`, `shutil`) script that:

- Walks each source class dir, collects `(abs_path, rel_path)` tuples.
- Shuffles training and test sources **independently** with a fixed seed (`SEED=42`).
- Splits **60% → `training_data_new`** and **40% → `to_be_classified_data_new`**.
- Copies files (preserving relative structure) into both new class folders.
- Originals are left untouched; prints per-class split summaries.

## 14. Data Visualizer (optional companion tool)

Spec: `Data_Visualizer_SPEC.md`. A separate Go binary that turns a feature-vector
CSV into a 2D PCA scatter-plot PNG — to see how scattered/overlapping the classes are.

### 14.1 CLI (`./data_visualizer`)

| Flag | Required | Purpose |
|---|---|---|
| `-input` | yes | feature-vector CSV (same schema) |
| `-output` | yes | output PNG path |
| `-dims` | no | PCA dimensions, default `2` (only 2 fully supported; `>2` rejected) |
| `-points` | no | max points per class, default `0`=all |
| `-legend` | no | draw legend, default true |
| `-json` | no | write `<output>.json` sidecar with per-point coordinates |

### 14.2 Pipeline (load → scale → PCA → color → render)

1. **Load** CSV by **name** (column position detected by header name); skip-and-count
   rows that fail to parse a number; treat empty `Traffic_Sign` as an error.
2. **Z-score standardize** all 22 numeric features (`mean_j`, sample variance with
   `n-1`; constant columns set std=1 so they contribute nothing). **Not** min–max.
3. **PCA**: build the covariance matrix (from standardized data), compute the top-2
   eigenvectors via SVD of the symmetric PSD matrix or Jacobi eigen-decomposition, and
   project each point onto PC1/PC2. Round-trip explained variance is recorded in the JSON.
4. **Color assignment**: one fixed per-class color, sorted class names to a stable palette
   (Okabe-Ito / Tableau 10 subset), cycling if more than six classes. A single entry per
   class is drawn with a small filled circle and thin darker outline.
5. **Render**: title `Traffic Sign Feature Scatter (PCA 2D)`, axes labelled `PCi (xx.x% variance)`;
   plot area padded ~5%; legend (with counts) if requested; PNG output deterministic per run.

## 15. Rebuild Checklist (faithful port notes)

For a rebuild in another language, ensure you preserve:

1. **One feature-vector type** consumed by both classifiers, exported/imported via CSV with this exact column order and formatting:
   - Integer color count; four `0/1` boolean flags; ten vertical + ten horizontal color-change counts stored as `(int/10)` to one decimal; nine white fractions (`[0,1]`) to two decimals; nine left–right asymmetries (`[-1,1]`) to two decimals.
2. **Color classification**: HSV with S,V in `0..255`, H in `0..360`; achromatic-first (black if `V<45`; white if `S<45 && V>150`); then red (`H near 0/360`), yellow, blue bands; unknown ignored.
3. **White frame removal**: min-max over non-white pixels where a pixel is white when `min(R,G,B) > 180`; fall back to full bounds if none found.
4. **Line scanning**: 10 vertical + 10 horizontal lines at relative intervals (÷11), sampling segments (`seg = len/100`, floored to 1), averaging RGB per segment, counting adjacent-segment category transitions; white→white is not a change.
5. **Grid features**: 3×3 cell grid for white fractions and left–right asymmetry; asymmetry = leftWhiteFraction − rightWhiteFraction per cell.
6. **Parallel extraction**: worker pool sized to `NumCPU`, distributing integer indices, writing into an index-aligned slice to preserve input order.
7. **KNN**: fit-on-train z-score using **population** std (`/n`); Euclidean distance; first `k` neighbors by sorted distance; majority vote; alphabetical tie-break; accuracy as percent with `int(accuracy+0.5)` rounding printed.
8. **Decision tree**: batch CART; Gini impurity; `minSamplesToSplit=30`; `maxDepth=12`; threshold = midpoint between adjacent sorted values; store class histograms; predict by routing on `feature <= thresh`; JSON serialization with pretty-print + the exact field keys (`feature`, `thresh`, `left`, `right`, `counts`) and `omitempty` semantics; leaves have `feature=-1`.
9. **Result string format**: `"Image <path> | Should be <label> | Classified as <label>"` (note the missing period at the end).
10. **CLI** two-pass parse: `-printfaulty` first, then mode flags with fixed positional args; trailing integer = k; default k=5; errors print `error: ...` and exit 1.
11. **Determinism**: ties broken alphabetically in both KNN and tree `majority`; color palette assigned by sorted class name; PCA output deterministic per run.
